## Compat finding 10: requesting `CapellaIncomingRelation` by patch does not change the result (hypothesis from finding 9 not supported)

**Result:** the patch was accepted and committed locally. The relation read back exactly like the first patched link, so the type name requested **makes no visible difference**. **Pending:** direction not confirmed in Capella (see item 9).

1. **Tool and call:** `apply_model_patch` with requirement `UR-B-01` (`b9ec03d9-dc96-43dd-a29d-9980479f0ab3`) as parent:
   ```yaml
   - parent: !uuid b9ec03d9-dc96-43dd-a29d-9980479f0ab3
     extend:
       relations:
         - _type: CapellaIncomingRelation
           target: !uuid 74ad58bb-90ae-4017-99ae-f41510b8681b
   ```
   (capability "Obtain ready-to-use coffee supplies in variety"). Then `resolve_model_uuids` and `generate_fabric` to read it back. Before the patch, `pull_model_changes` returned up to date.
2. **Context:** Capella 6.1 model `K Cup Coffee Maker.aird`; model before: `45acd73` (pushed, includes the engineer's Capella-drawn "Satisfy" link). New local commit: `55ef3ba5` (**not pushed**).
3. **Expected vs actual**
   - Hypothesis (finding 9, observation A): the type names might be swapped between input and result, so requesting Incoming might give the satisfy-direction `CapellaOutgoingRelation`.
   - Actual: status `ok`, committed. UR-B-01 now has one relation, UUID `0e4e70c4-e630-4810-9b18-996ddbcf869c`, type **`CapellaIncomingRelation`**, empty name and description, **no source or target shown** in the read-back. This is the same type and the same read-back profile as the first patched link (finding 7, requested as Outgoing), which the engineer confirmed to be reversed.
4. **Conclusion:** requesting Outgoing (finding 7) and requesting Incoming (this finding) both give a `CapellaIncomingRelation`. The type requested in `_type:` appears to be ignored on the requirement's `relations` property, and the stored type does not depend on it. So the apparent "swap" in finding 9 was not a swap; the patch route always produces the same kind of link, and the link drawn in Capella is a different kind (`CapellaOutgoingRelation`, named "Satisfy").
5. **Likely direction, inferred:** because the stored type and the read-back match the first patched link, this one is **probably reversed as well**. This is an inference, not confirmed in Capella.
6. **Reproduction:** open a session at `45acd73`, run the patch above, then `generate_fabric` with UR-B-01 resolved.
7. **Scope:** unknown; appears to come from how the library creates relations from the requirement's side.
8. **Workaround:** none by patch so far; satisfy links are drawn in Capella.
9. **Check in Capella 6.1:** not done. Pushing this commit would let the engineer confirm the direction, after which the link would be deleted again; alternatively the local commit can be dropped without pushing.
10. **Tool version or build:** not known (open item in DEC-0007).

**Suggestion to the tool maintainer:** either honour `_type` when creating a relation from the requirement's side, or provide another way to create a relation owned by the capability or module with the satisfy direction (the kind Capella creates when linking an element to a requirement), and show source, target and name for both relation types in the read-back.
