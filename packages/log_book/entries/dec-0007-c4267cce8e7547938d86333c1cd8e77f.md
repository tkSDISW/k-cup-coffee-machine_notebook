## Decision: this project also tests `capella-fabric` against Capella 6.1, and findings go back to its maintainer

**Decided by the engineer.**

**Context (as described by the engineer)**
- The `capella-fabric` tools originated on Capella **6.1** and have since been updated to support **7.0.1**.
- The agent known as "cousin" (a Claude instance that maintains the tools) has built a test suite on **7.0.1**.
- This project is built on Capella **6.1** (DEC-0006), so working on the model also exercises the tools against 6.1.

**Decision**
- Treat compatibility testing on 6.1 as a secondary goal of this project, alongside the educational model.
- **Record every finding in this notebook as it appears, then provide the findings back to the maintainer.** This applies to both problems and confirmations that something works, since the 7.0.1 suite does not cover 6.1.

**What a compatibility finding records** (one entry per finding, titled "Compat finding: ..." so they can be collected)
1. **Tool and call:** tool name and the arguments used, with any patch text.
2. **Capella and model context:** Capella version (6.1), the model commit before and after, and the model phase and element UUIDs involved.
3. **Expected result and actual result,** including any error text.
4. **Reproduction steps,** short enough for the maintainer to rerun.
5. **Scope:** whether it looks specific to 6.1, to the tools, or to this model's content; state if unknown.
6. **Workaround,** if one was found.
7. **Check in Capella 6.1:** whether the model opened and displayed correctly after the change, since the tools cannot confirm this themselves.
8. **Tool version or build,** if it can be determined (see open items).

**Conventions**
- **Neutral wording applies:** findings describe behavior and evidence, without blame or judgment about the tools or their authors.
- Confirmations are logged too, in brief ("tool X worked on 6.1 for operation Y at commit Z").
- Findings are kept separate from the modeling decisions so they can be exported without the educational narrative.

**Status so far:** reading works (see OBS-0005); no problems found yet. Writing has not been tested.

**Open items**
1. Find out how to identify the tool version or build (from the server or from the maintainer), so each finding can name it.
2. Agree how findings are handed back (a periodic summary from this notebook, or entry by entry), and in what form the maintainer prefers.
3. Ask what the 7.0.1 test suite already covers, to focus 6.1 testing on operations it does not exercise (for example patches, `verify_model`, `pull_model_changes`, `push_model_changes`, diagram rendering).
