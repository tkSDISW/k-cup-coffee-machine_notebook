## Decision: traceability convention is model element to requirement, with a "satisfy" meaning

**Decided by the engineer**, while reviewing the first requirement link test (Compat finding 7).

**Convention.** Requirement links point **from the model element back to the requirement**, with a **satisfy** relationship: a capability (and later a function, component or other element) satisfies a requirement. This matches the paper's guidance (DEC-0010) that textual requirements are linked to the model elements that satisfy them.

**What this means for the work so far**
- The capability numbers listed in each requirement's description (from NOTE-0002) are the plan for which capability satisfies which requirement.
- The one link created by patch (UR-B-04 and "Prepare a serving of hot coffee on demand", commit `85b33268`) was created from the requirement's side. It reads back as a relation of type `CapellaIncomingRelation` owned by UR-B-04, but its source, target and direction **cannot be read from the tools**, so it is **unverified against this convention**. The engineer's check in Capella will settle it.
- A patch from the element's side was tried and refused (Compat finding 8), so the tools may not be able to create links in the satisfy direction, or to set a "satisfy" relation type.

**Plan, to confirm**
1. The engineer inspects the pushed UR-B-04 link in Capella and reports its direction and type.
2. If it matches the convention, the remaining links are created by patch in the same way, from the capability numbers in the descriptions.
3. If it does not, the engineer removes it in Capella and links are drawn in Capella until a patch shape works; the finding goes back to the tool maintainer with the request that element-to-requirement links with a relation type be supported.

**Open item:** the requirement-to-capability mapping by capability number is a first pass and gets reviewed with the capabilities when tuning is finished.

---

**Update: plan resolved.** The engineer confirmed in Capella that the patched link was reversed, and will **delete it and create the satisfy links in Capella** (the third option in the plan above). Requirement-to-capability links are therefore drawn in Capella, using the capability numbers in each requirement's description as the starting mapping. After the engineer pushes, the agent pulls and reads the links back. Details are in Compat findings 7 and 8.

---

**Update: first satisfy link in place.** The engineer replaced the reversed test link with one drawn in Capella (commit `45acd73`): UR-B-04 and "Prepare a serving of hot coffee on demand", a relation named "Satisfy" of type `CapellaOutgoingRelation`. It is the only requirement link so far; the other 15 requirements have none. Read-back details and the comparison with the patched link are in Compat finding 9. Next link-related step, to decide: test by patch whether requesting `_type: CapellaIncomingRelation` from the requirement's side gives the satisfy direction (one pair, checked in Capella), or draw the remaining links in Capella.
